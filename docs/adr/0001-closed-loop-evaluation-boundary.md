# Close the tracking loop through a simulated camera

The first closed-loop milestone exercises the real C++ detector, tracker and scheduled controller, with dispatched movement rotating a simulated camera around a fixed screen-center aim point. Targets move independently. This retains production tracking behavior while making camera response observable and avoiding desktop cursor movement; actual Windows mouse injection and serial-device delivery are separate later integrations.

Initial acceptance evaluates correct-target following, aiming error, recovery, overshoot, oscillation and observation-to-applied-movement latency. Automatic firing and recoil interactions are deferred until the tracking loop is validated. This records the confirmed design boundary; implementation is a separate phase.

The first scene library uses curated photographic targets and backgrounds with explicit target identities and linked head/body aim points, rendered through a perspective camera. Horizontal and vertical field of view and mouse-count-to-angle sensitivity are configurable and initially uncalibrated; application-specific accuracy claims require later calibration. Simulated output preserves the chosen backend's gain, rounding and command splitting before delivery to the simulated camera. Natural detector failures and faults injected after inference are scored in separately labeled runs.

Each scene provides time-stamped truth for target world position, visible head/body aim points, occlusion and intended identity. Initial selection is scored separately; switching aim point within one target is not an identity switch. World truth continues during occlusion or off-screen motion. After the configured loss deadline, tracking movement must stop until distinct observations reconfirm the target. The camera model separates backend transforms, transport delay and quantization, camera sensitivity and independent external shake.

The first suite includes 500–6000 px/s motion across target sizes and observation cadences, crossing targets, temporary occlusion, missed/noisy detections, crop exits, reversals and external shake, first individually and then in selected combinations. Report wrong-target movement time, identity switches, normalized error at applied movement, time within target region, loss/recovery, overshoot and oscillation separately from latency stages. Do not collapse these into one score. Interactive setting changes start new scored segments with frozen configuration, model, assets and seed.

The tracker receives detector output and ordinary capture metadata only. Ground truth, intended identity and future motion belong exclusively to the evaluator. Compare candidates with the frozen default policy on identical scenes and seeds. Harness correctness violations fail immediately; quality gates are calibrated from evidence. The existing motion candidate remains opt-in while its combined-disturbance wrong-target movement regression persists.

Curated scored assets record source, license, annotation version and train/validation split, beginning with a small hand-checked set. Existing detection labels lack persistent identity and head/body linkage and cannot serve alone as scored scene truth. Saved browser reports synchronize scene, detections, identity, camera/aim traces, commands and metrics with machine-readable events. Pausing or scrubbing a live run views its saved recording; the live world clock continues.

Both modes execute the production controller and servo scheduling through an injected simulated output adapter, including fractional movement, limits and freshness checks. The existing replay dispatch approximation is insufficient for full-loop claims. The first renderer is a 2.5D scene: photographic targets and backgrounds at explicit depths projected through camera field of view, with simple occlusion and no pose animation. Scenario selection contracts specify intended initial identity, allowed handoffs and head/body rules; initial selection and continued following are scored separately. The simulator has an explicit no-device mode, clear run-mode indicator and saved configuration fingerprint. Actual device delivery remains a separate future integration.
